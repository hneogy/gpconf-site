**S-001 — Static site, Python build, no framework.** Seven pages of mostly prose with two reading levels each, plus small client-side tools and charts, do not need a JavaScript framework. The build is one Python script (`build.py`, Jinja2 templates, ~150 lines) producing plain HTML into `dist/`; the scheduled jobs are Python too, so the repository has one language. Jinja2 is the only dependency and is pinned in `requirements.txt`. Considered and rejected: Eleventy or Astro (a Node toolchain for template inheritance alone), hand-written HTML (seven pages × shared header, footer and toggle would drift), committing `dist/` (generated noise; Cloudflare Pages builds it).

**S-002 — Hosting: Cloudflare Pages Git integration, Python build.** Cloudflare's current (v3) Pages build image ships Python 3.13 and pip and honours `.python-version`; the build command is `pip install -r requirements.txt && python build.py`, output directory `dist`. Every commit, including the jobs' data commits, triggers a rebuild, which is how the pages get fresh values without client-side fetching. To be confirmed when the project is connected; the fallback is a GitHub Actions deploy with `wrangler pages deploy`, which needs an API token the owner would create.

**S-003 — Pages are rendered from the jobs' JSON at build time.** The home, tracker and library pages carry their numbers in the HTML, so they work without JavaScript and search engines see them. JavaScript adds only the history charts (fetching `/data/tracker/history.json` from the same origin) and the two tools. Nothing on any page contacts anything but this origin; the CSP (`default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; form-action 'none'`) enforces it. No external fonts, images or scripts, so the Zenodo DOI badge is a text link.

**S-004 — Reading level is a client-side toggle over duplicated content, default Simple.** Each page contains both versions in `.lvl-simple` and `.lvl-technical` blocks; a pre-paint script applies the stored choice (`localStorage`, key `gpconf-level`) or `?level=` and defaults to Simple; with scripts off both versions show with labels. Rejected: two URL trees (double the pages to link and index; the toggle would be a navigation) and server-side variants (the choice must persist across pages instantly).

**S-005 — Fetch budget and rotation.** Five daily endpoints (the last-30-days CSV and TLE, the analyst CSV and TLE, the Starlink SupGP CSV) plus stable-source drift checks. The corpus has 22 stable CelesTrak sources; re-fetching all of them one day a week would be 27 requests that day, over the owner's ~10/day. Instead each source is due 6.5 days after its last check and the job takes at most 4 due sources per run, oldest first, so every source is checked about weekly and no run exceeds 9 requests. The fetcher refuses a repeated URL and enforces a hard cap of 10 before sending anything; no redirects, no retries, 2 s between requests, a User-Agent naming the project and site; tested in `tests/test_tracker.py`. One expected 404 a day (the last-30-days TLE) is far under CelesTrak's 50-errors-per-2-hours threshold.

**S-006 — Derived measurements only, by construction.** The tracker computes record counts, the highest id, six- and nine-digit counts, the HTTP status of the TLE request, count relations, and per-source SHA-256 comparisons; the outputs never contain a field other than `NORAD_CAT_ID`-derived integers, statuses, byte counts, hashes and timestamps. Raw bodies stay in memory in CI; a local `--cache-dir` (git-ignored) exists for inspection. A test asserts that no element value from the test input appears in any output. The library job stores verdicts, versions and exception text only.

**S-007 — Worked examples.** The only element sets on the site are (a) the CCSDS 502.0-B-3 annex G OMM example (GOES 9) as printed in the standard and as rendered into a TLE by the corpus renderer (checksums verified), used for the side-by-side, the anatomy tool, the highlighted provider-convention columns and the library reproducers; and (b) the corpus's published derived Alpha-5 line for catalog 100000 (SARAMAGO, first record), whose provenance sidecar is public. **S-022 — Drift classification fixed and four false "drift" results repaired.** On 2026-09-22 at 06:44 UTC every request of the scheduled run, including the four weekly drift checks (`gp-first-100000-XML`, `gp-first-25544-2LE`, `gp-first-25544-CSV`, `gp-first-25544-JSON`), received HTTP 500 with the same 1,074-byte error page, SHA-256 `e6d27d46a908d95c2b7a93ca5a1329dfb80eeea54a9c35ec0e150cf2f2623872`. The fetcher records an HTTP error's status and body without setting `error`, and `run_drift` compared the hash of anything without `error`, so the error page was compared with the recorded hashes and all four sources were marked "drift"; the tracker page then showed "4 drift" in red from that morning until this fix was deployed, a false statement about the corpus's gp-first stability assumption. Rule now (`classify_drift`): a 200, or the 404 recorded for the two 16-byte "No GP data found" sources, is an answer and is hashed; a 200 where 404 was recorded or the reverse is "drift", the alarm S-009 asks for; any other status (5xx, 403, 429), or a transport failure, is "error". An error does not touch `last_checked`, so the source stays due, and does not record the page's hash as the source's; it sets `last_error_at`. The tile shows the error count and turns amber on errors; the per-source table shows the error time. A regression test covers a 500 page, a matching 404, a 404 that became data, and a source whose earlier success stands. Repair of the recorded data, with the values shown in the commit: the four sources' `last_status` "drift" → "error", `last_checked` (2026-09-22T06:44:55Z to 06:45:01Z) → null with that time moved to `last_error_at`, the error-page `last_sha256` removed, their history entries "drift" → "error"; the day's `drift.results` in `history.json` "drift" → "error"; `latest.json`'s drift summary recomputed (4 match, 0 drift, 4 error, 14 never checked) with its fetch log kept.
