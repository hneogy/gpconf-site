The world ran out of five-digit satellite numbers. Does your software know?

On 11 July 2026 the satellite catalog reached number 100000. Much older software can quietly lose every satellite catalogued since. This is a free test kit that shows developers exactly where their code breaks.

A conformance corpus for parsers crossing the five-digit catalog-number boundary

Eighteen cases built from real CelesTrak responses and published specification vectors: Alpha-5 TLEs, six- and nine-digit NORAD_CAT_IDs, CCSDS OMM in CSV, JSON, XML and KVN, one writer-side case for tools that produce TLEs, and one that hands a parser corrupt input. Every expected value traces to a recorded URL, retrieval time and SHA-256. Point the runner at your parser, or at the TLEs your tool writes; it tells you, case by case, what breaks and why.

Test your own softwareInstall

If you have Python, the test kit installs with one command and comes with ready-made connectors for several popular libraries, so you can test one without writing any code. The third line downloads, once, the real satellite data it checks against.

Since v0.3.0 the runner installs from PyPI with the corpus’s own files; the provider data is fetched once, under CelesTrak’s usage policy, into a per-user cache. Standard library only, Python 3.9 or later.

pip install gpconf
gpconf run --preset reference   # before any fetch: 5 cases run, 13 need provider data
gpconf fetch                    # once: ~60 requests, 2 s apart, cached
gpconf run --preset reference   # then all eighteen

A preset tests a library with no adapter written; gpconf presets lists them (reference, naive, sgp4, pyephem, satellite.js, tle.js, tle.js-api), and the adapter guide covers writing your own. In a GitHub Actions job, three lines run a preset against your library, offline and report-only:

- uses: hneogy/gp-omm-conformance@v{{ corpus.version }}
  with:
    preset: sgp4
